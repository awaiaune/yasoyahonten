# 決済・注文・在庫の耐久化（ローカル実装）

本番デプロイ、実Square API、認証情報、既存の実DBへの操作は行っていない。dev/local-isolation上の未コミット変更。

## 実装した契約

- クライアントは注文UUIDをlocalStorageに保存。二重送信中と完了後の再送を抑制し、再読み込み・応答切断時はstatus APIで先に確認する。結果不明でカードを再トークン化しない。
- サーバーはUUID必須。旧クライアントからUUIDなしの要求を受けても自動で新キーを作らない。購入時の商品・金額・配送先のハッシュが違う再送は409。
- DOに見積・配送先・注文番号・固定Square決済キー・状態を先に保存してから決済。カードトークン、秘密鍵は保存しない。
- 同じグローバルDOのキューでHTTP処理とalarm処理を直列化。再起動時にもDO storageの台帳とbarrierを読む。
- 支払状態: prepared → submitting → paid / unknown / declined。決済要求は新規attemptにつき一度だけ。再送は照合・復旧に限定する。
- Squareから応答が得られなければunknown。既知のpayment IDで取得、または作成時刻付近からPayments一覧をページングしてreference_idを照合する。金額・通貨・Locationも検証。複数一致、走査上限、取得不可、不一致は要確認。
- 一覧にないことを「未課金」と解釈しない。新しいキーでの自動再課金はしない。確定したFAILED/CANCELEDのみdeclinedとし、その注文を再課金しない。クライアントは確定失敗後に次の明示的操作で新しい注文を作れる。
- 在庫操作キーとoccurred_atを送信前にDOへ保存。再試行で同じ内容を使用する。失敗・応答喪失・期限切れを記録。
- D1は既存ordersへの投影。INSERT OR IGNORE後にpayment ID一致を確認し、在庫フラグのみ更新。発送済み状態、追跡番号、過去明細は上書きしない。
- D1への投影が失敗しても、DO内の支払済み記録から復旧。クライアントへ202と照会手段を返し、カートと注文UUIDを保持。
- 在庫または支払状態が不明な間はbarrierで新規購入を503停止。支払済み・D1保存済みの注文は成功として扱い、在庫要確認は管理者向けに保持。
- alarmによるバックオフ再試行と認証済み管理者APIを提供。最大8回で手動確認。1時間を超えた在庫操作は自動再送しない。この時間は保守的なローカル方針で、Squareの保証期間を検証した値ではない。

## API

- POST /api/payments: attemptId（UUID v4）、sourceId、items、contact。既存の成功フィールドを維持。
- POST /api/payments/status: attemptIdのみ。新規決済を行わず照合・復旧する。UUIDは照会用capabilityなので推測困難な値を使いログやURLへ出さない。個人情報は返さない。
- GET /api/admin/payment-attempts: ADMIN_TOKEN認証。未解決注文のphase、inventoryState、orderState、warning、注文番号を返す。
- POST /api/admin/payment-attempts/:UUID/recover: ADMIN_TOKEN認証。同じ処理を何度呼んでも新規課金しない。上限を超えた操作や期限切れを強制適用する機能は作らない。
- 既存の注文一覧、詳細、発送APIとHTML/CSSは維持。

管理画面の次の追加案: 未解決件数と「支払確認中」「在庫要確認」「D1保存待ち」「手動確認」を表示し、安全な再照合ボタンを置く。顧客へ再購入を案内しない。今回はAPIまで実装し、既存画面のデザインは変更しない。

## データ・マイグレーション

D1スキーマ変更はないため、D1マイグレーションは不要。既存ordersのinventory_adjustedを利用する。
DOの既存SQLite対応storageに attempt:UUID と barrier を追加する。削除・初期化・既存行の移行はしない。
台帳には配送先を含むため、将来の本番化ではアクセス権・保存期間・削除方針・監査を定める。初期実装では重複防止に必要な記録を勝手に期限削除しない。
過去の旧フローによる決済は台帳がないため自動修復の対象外。Squareと既存D1を別途照合する移行計画が必要。

## ローカルテスト

リポジトリルートで npm --prefix dev test。
既存隔離テストを変更せず残し、payment-safety.test.mjsとcheckout-safety.test.mjsを追加。
Square代替はテスト時だけ設定するLOCAL_SQUAREサービスbinding。sandboxかつLOCAL_TEST_MODE=1以外では使用不可。通常の分離サーバーにはbindingもテスト認証値も注入しない。
外向きfetchの拒否は継続。テスト用DB・DO状態は/tmpに作る専用の新規領域。実際のローカル注文DBを削除・初期化しない。
ブラウザの二重タップはDOM/Square SDK/fetch代替を使ったVMテスト。Android実機や本物のSquare SDKを検証したものではない。

## 残る制約・本番化前の確認

- Square POSや他サイトの在庫変更はDOと排他できない。支払直後に外部で在庫が減るケースは「支払済み・在庫要確認」として停止し、手動対応する。完全な売越し防止は保証しない。
- APIの冪等性保持条件・在庫操作の再送保証・一覧の可視性と取得権限・Location別の挙動は実APIで未確認。今回の代替実装での成功を本番の保証に置き換えない。
- 拒否応答でもSquareの確定した決済IDが得られず一覧照合できない場合は、安全のためunknownで停止する。強制解除・自動返金は未実装。
- Payments一覧の走査は最大20ページ。見つからなければ要確認。Webhook、定期的な全件照合、返金／紛争の反映は今後の実装。
- 既に完了した注文の外部返金を追跡する仕組みは未実装。完了後の同じ注文再送は保存済み結果を返す。
- 未解決注文が一件あると全購入を止める保守的実装。将来SKUごとの予約・停止範囲の縮小を検討する。
- メールは既存同様best effort。emailAttemptedを先に保存し重複起動を避けるが、送信直前のクラッシュによる未送信を自動救済しない。メールoutboxは別作業。
- 手動の強制再課金、在庫補正済みの宣言、保留解除は誤操作の影響が大きいため未提供。監査つきの安全な手順を後続設計する。
- 旧ブラウザキャッシュはattemptIdを送れないため400で停止する。本番移行時のキャッシュ更新・ロールアウト計画が必要。
