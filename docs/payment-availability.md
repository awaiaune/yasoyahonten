# 注文・バリエーション単位の保留と無人復旧

この文書は payment-safety-implementation.md の「共通barrierで全購入を停止する」方針を置き換える。ローカル実装のみ。本番アクセス、デプロイ、Git操作による公開は行わない。

## 何が停止するか

| 異常 | 購入への影響 |
|---|---|
| 決済結果が不明／照合待ち | 当該注文の商品バリエーションのみ保留。他バリエーションは販売継続 |
| 在庫減算の失敗・応答喪失 | 同じバリエーションのみ保留。複数商品注文なら全対象を保留 |
| 決済と在庫減算が確定し、D1保存だけ失敗 | 当該注文のみ保存待ち。同じバリエーションも販売継続 |
| 確定した決済失敗／キャンセル | 当該注文は失敗。全対象の保留を解除 |
| 台帳の永続保存自体ができない | 新たな課金をしない。DO等の共通インフラ障害は正常販売を保証できない |

在庫を再取得するので、保留解除は「販売可能数がある」ことを保証せず、実在庫ゼロなら通常どおり購入不可。

## 排他・耐久記録

既存の全購入を処理するDurable Objectと直列キューは維持。注文ごとに固定の決済キー・在庫キー・在庫操作日時を保存する。
Location ID + Square Variation IDを排他単位とする。一つの注文が複数バリエーションを含む場合は全対象を保持し、別注文が同じ対象を課金することを防ぐ。

DO storageへの一回のputで以下を原子的に更新:
- attempt:UUID: 処理台帳（個人情報を含むため管理対象）
- sku-holds: 対象ごとの保留所有者。解放時は当該注文の所有権だけを除去
- pending:UUID: 未解決注文の巡回索引

決済前に台帳と保留を保存する。未確定状態ではキーを変更した再課金はしない。既知IDまたはreference_idでSquareの結果を照合する。一覧に見つからないことを未課金の根拠にしない。
既存の旧barrier台帳は初回アクセス／Alarmで全件ページングし、保留と索引を再構成。旧記録・既存注文は削除しない。D1スキーマ変更はない。

## 無人の自動復旧

Durable Object Alarmを利用するため、ブラウザを開く必要はない。Cron Triggerの新設は不要。再起動後も永続Alarmと索引が残る。

- 初回は約30秒、以後バックオフ。複数の保留注文を巡回し、一件の異常で他の復旧を打ち切らない。
- 一回のAlarmで外部復旧を行う注文は一件とし、次の仕事へ進む前に購入キューを解放する。巡回カーソルを保存し先頭注文の固定的な優先を避ける。
- 各通信は最大5秒、決済一覧の走査は合計約5秒／最大20ページ。遅い照合が際限なく購入を待たせない。時間内に見つからなければ未確定のまま次回照合。
- 顧客のstatus照会はバックオフ前に復旧回数を消費しない。管理者のrecoverは時刻前でも安全な再試行を要求できるが、手動確認へ移った在庫操作を強制実行しない。
- 決済照合、同じ内容の在庫更新、D1投影が自動対象。最大8回の回復試行後は手動確認へ移る。
- 在庫更新は固定キー・日時・payloadでのみ再送。初回操作から1時間を超えた不明操作を自動で再送しない。
- 在庫が手動確認になっても、支払済み注文のD1投影は別に最大8回まで自動再試行する。
- Alarm処理の途中の保存失敗に備えて先に安全用Alarmを置き、他注文を含む次の巡回を残す。

## 自動復旧できない場合と通知

金額・通貨・Location・注文番号の不一致、確定した在庫競合、在庫の再送安全期間超過、試行上限は管理者確認へ。
対象バリエーションは保留したまま、無関係な商品は販売できる。

既存Resend送信関数を再利用し、ORDER_NOTIFICATION_EMAILへ「要確認」の注文番号・理由・対象商品IDを通知する。顧客連絡先やカード情報は通知に含めない。
通常の一時障害では異常通知しない（従来の注文メールは別）。通知も固定のIdempotency-Keyを使い、応答喪失時は同じ内容で再送する。未送信は5分間隔で再試行し、最初の送信から1時間を超えた不明メールは重複回避のため自動再送を止める。
メール設定なし・送信不能・通知期限切れは管理者APIのnotificationStateに残る。メールが必ず届くという保証はない。今回のローカル通常起動はメール認証情報を持たず、テスト専用LOCAL_RESEND bindingでのみ通知を検証する。

管理者は既存の認証済みpayment-attempts APIで全未解決注文・pausedVariations・manualReview・notificationStateを確認できる。管理者recoverは上限後でも決済の読み取り専用照合とD1投影を再要求できる。厳密に一致した確定結果だけを採用し、新規課金は行わない。在庫の期限切れ・確定競合は強制適用しない。画面への追加、強制保留解除、自動返金は未実装。後から手動照合し、決済ID・在庫操作・D1を確認した上で監査付きの解除／補正機能を別作業として設計する。

## 限界と本番化前の確認

- DO内の購入同士の超過販売は防ぐが、Square POSや別販売経路とは原子的な排他にならない。確認直後に外部で最後の1個が売れるケースは、支払済み・在庫競合として当該対象を保留する。現構成のまま外部を含む完全な超過販売防止は保証しない。
- 409を確定在庫競合として扱うローカル方針。実Squareのエラーコード、在庫調整の非負保証、冪等性保持期間、API照合権限・ページング・結果可視性は未確認。
- 共有DOキューは維持しているため短時間の待ち合わせは残る。仕事の大量化時には索引掃除・走査バッチ化・DO容量・監視を評価する。
- 旧台帳の初回索引再構成は全履歴を読み、相応の時間がかかる。本番移行では事前の負荷・件数評価が必要。
- 通知は既存Resendの設定とドメイン認証が必要。通知設定欠落や長時間のメール障害には別系統の監視を検討する。
- 本番でAlarmが有効に動くこと、運用時の通知先、管理者UI、個人情報の保存期間、外部Webhook・返金照合は別途検証／設計が必要。
- 既存商品のID・価格・送料・URL・HTML/CSSを変更せず、既存注文・発送情報を保持する。テストは隔離DBと代替Square／Resendのみを使用。

## ローカル検証結果

`npm --prefix dev test`: 29件成功、失敗0、スキップ0。
既存の隔離・二重タップ・再送・クラッシュ・D1障害・在庫二重減算防止を維持。
追加で、異常SKU以外の販売継続、残り1個への並行購入、混合カート、複数保留の独立解放、D1のみの障害中の同SKU販売、旧台帳の再索引、128件を超える巡回、復旧上限後の管理者照合、通知応答喪失と再起動後の冪等再送、通知期限切れを確認。
実際のMiniflare Durable Object Alarmが再起動後に発火し、画面・復旧APIを呼ばずに注文投影と在庫更新を完了することも確認した。外部サービスはテストbindingだけを利用。
