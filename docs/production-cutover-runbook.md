# 初回切替と無停止更新の標準手順

2026-10-27更新。Web実注文0件はユーザー確認情報。初回だけ短時間の新規Web決済停止を許容する方針へ変更。現時点で停止・デプロイ・DNS変更・SQL実行はしていない。

## 評価と今回の追加

Phase 3の管理権限、専用Access、既存ID/SKU照合、追加D1スキーマ、購入台帳を維持する。追加はv1契約・購入画面、購入受付フラグ、キャッシュ対策、配布ソースのハッシュ記録。namespace、固定Object名、購入台帳形式にPhase 3からの追加変更はない。これは実稼働Versionと状態形式が同一だと確認した意味ではなく、初回反映前の実照合は必要。今回は新規D1マイグレーションは不要。管理用0001/0002は別承認まで未適用のまま。

旧クライアントとの完全な無停止互換は初回導入の必須条件から外した。旧画面は非2xxで安全に拒否し、新画面と新APIを同じ切替窓で公開する。初回以降はv1を維持しながら追加型で更新する。

## フラグと配布物

PRODUCTION_CHECKOUT_ENABLED='0' は新規購入だけを停止する。'1'で受付可能。ただしPRODUCTION_PURCHASE_PROTOCOL='durable-v1' が未承認のままなら新クライアントのcapabilitiesは受付不可。PRODUCTION_CHECKOUT_ENABLED未指定・不正値は新規受付を拒否する。テストの通常稼働条件でも明示的に1を設定し、設定漏れで受付が再開しないことを確認する。配布テンプレートは明示的に0。停止中もstatus、既存注文の在庫減算・D1保存・通知・Alarm復旧を止めない。既にSquareへ送信済みの決済を取り消す機能ではない。

production/checkout-cutover.example.jsonc は購入切替専用の非デプロイ用テンプレート。追加R2・Access・管理schemaに依存せず、MANAGEMENT_ENABLED=0を維持する。実Account・稼働設定・Secret名・Cron/Observability・DO migration履歴を照合してからGit対象外の設定を準備する。現在のworker/wrangler.jsoncをそのまま使って新コードを本番deployしない。

node production/release-review.mjs prepare → check で、購入画面・JS・Worker/管理依存コード・CSS等のSHA256、契約番号、固定DO識別子をローカルのGit対象外JSONへ保存する。再生成はレビューの代わりではない。既存のcheckが失敗したら変更内容を再レビューし、承認済み配布物を確定する。これはソースの照合であり、実際のビルド成果物・Secret・実バインディングの検証ではない。

## 初回切替（すべて別途承認後）

1. 実稼働Version/設定/DO namespace/マイグレーション履歴、Square ID、未解決注文・決済がないことを読み取りで確認する。Web注文0件でも作業直前に未確定の購入があれば切替を止める。顧客本文は不要。
2. GitHub main公開とCloudflare Workers Buildsの連動を確認する。静的サイト公開時に、旧worker/wrangler.jsoncで意図しないバックエンド自動デプロイが走らないよう、単一の反映経路を承認して準備する。自動デプロイの停止や設定変更も別途承認。main変更は今は行わない。
3. 既存設定と直前Version、配布物を記録。必要なバックアップと保持期限を確保する。namespace/class/binding/固定Object名を変更せず、新バックエンドをPRODUCTION_CHECKOUT_ENABLED=0で反映する。**旧稼働コードはこの新フラグを解釈しない可能性があるため、旧コードへフラグを追加しただけで停止したとは判断しない。** 新バックエンドへの反映と受付停止を一体の操作として扱う。
4. GET /api/v1/checkout-capabilities のcontractVersion=1、checkoutEnabled=falseを確認する。旧画面の要求も503/409等で拒否されることを承認済み範囲で確認する。停止直後にも処理中・未確定のWeb購入が残っていないか確認し、残る場合は停止を維持して照合する。注文・決済・在庫を書き込む試験を勝手に実施しない。
5. 同じ切替窓でcheckout.html、新checkout-v1.js、従来scriptを保持した静的ファイル一式を公開する。商品URL・価格・送料・Square設定値は維持する。旧クライアントが残ってもサーバー側で安全に拒否する。
6. Androidの通常画面・再読込画面でメンテナンス表示とAPI版を確認する。新JS参照・CORS・実Cache-Control・ログ・配布ハッシュを照合する。クライアントの注文IDやlocalStorageを一括消去しない。
7. 承認後PRODUCTION_CHECKOUT_ENABLED=1へ切り替える。新画面は更新後に受付状態を確認し、購入可能となる。実決済・実在庫を伴う受入試験は対象と金額を別途承認。管理書き込みはまだ有効化しない。
8. 購入エラー率、処理時間、pending/review件数、SquareとD1の件数・状態、在庫差異、通知失敗を監視する。ログへ個人情報・カードトークンを出さない。問題時は新規受付だけを0へ戻し、同じIDの復旧を続ける。

## 切り戻し

初回には稼働実績のあるv1旧版がない。問題時は受付停止を維持して修正し、安易に旧ランダム決済キー方式へ戻さない。新しい注文台帳・保留注文が存在する間、旧購入Workerへの復帰は停止条件。静的HTMLだけ戻すと旧画面の購入が拒否され続けるため、販売再開とは扱わない。

初回受入後は、そのv1互換のWorker Version・設定・ソースハッシュ・静的ファイル一式を既知の正常版として記録する。受入済みのrelease-review.jsonだけをローカルのproduction/.generated/known-good-release.jsonへ保存し、次回からnode production/release-review.mjs compareも必須にする。現在は初回未公開なので正常版の記録を捏造しない。以後はv1契約と新旧DO状態を読める直前版だけへ戻す。DB/R2/DOの削除・初期化・全体巻き戻しはしない。D1追加テーブル・列は残し、旧コードが未知の任意項目を無視できる期間を設ける。SQLの破壊的変更は別のメンテナンス計画へ分離する。

## 次回以降の標準手順

開発 → ローカル回帰 → Sandbox受入 → 実設定との差分レビュー → 新旧クライアント/DO状態の互換試験 → 本番反映 → 監視 → 必要ならv1互換の正常版へ切り戻す。

| 変更 | 原則 |
| --- | --- |
| 商品写真・文章・管理UIの改善 | API契約を変えず無停止で反映可能 |
| 既存機能フラグの有効/無効 | 依存条件を確認して独立に反映。保留ジョブ/購入復旧は維持 |
| APIの任意項目・管理機能追加 | 旧クライアントが無視できるなら無停止候補 |
| D1追加テーブル・nullable列 | expand → 新旧共存 → データ検証。ロック/負荷次第では作業窓が必要 |
| 必須項目・意味・主要応答の変更 | v2を追加しv1と共存。旧版撤去を急がない |
| DO状態変更 | 旧状態読取と新状態の切り戻し互換を証明できれば無停止候補 |
| DO namespace変更、破壊的SQL、互換性のない復旧方式 | 通常更新から除外。専用計画・停止条件・別承認が必要 |

段階的トラフィック配分、CI/CD、監視自動化は未実装。契約・状態が非互換のWorkerを、同じDOにランダム配分して安全だとはみなさない。まず手動の互換性レビューと単一反映経路を標準化する。公開済みの購入JSファイルは上書きせず、次のUIには別のファイル名（同じAPI v1を使うcheckout-v1-r2.js等）を追加し、旧ファイルを保持する。compareは公開済み購入JSの変更・削除、API majorの削除、DO識別子変更を拒否する。クエリ付き参照だけを不変配布の保証にしない。
